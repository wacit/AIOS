The scripts detect what they are running on, so the same files work on the Windows desktop and on the Ubuntu VM (walt-ai). The tuned defaults assume this box; on different hardware the auto-selection picks a quant that fits and you adjust from there.

Step 1 — Prerequisites

  1. NVIDIA driver that knows about Blackwell

    Anything 570+ on Windows; on Ubuntu sudo ubuntu-drivers install or nvidia-driver-580. Confirm with nvidia-smi showing both cards and compute_cap 12.0. The build scripts do not install the driver — only the toolkit.

  2. Disk space

    About 6 GB for the CUDA toolkit, 3 GB for the llama.cpp build tree, and 17 GB per model quant. Put models/ on the NVMe.

  3. Internet for the first run

    winget/apt downloads, the GitHub clone, and the Hugging Face model pull. Later re-runs only fetch new commits.

  4. Windows only: PowerShell execution policy

    Launch with -ExecutionPolicy Bypass as shown below, or run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once. If winget has to install Build Tools or CUDA it will prompt for elevation.

Shortcut: AIOSSteps 2–4 can be done from the browser instead: python aios.py, then Build → pick a model (the recommender marks the quant that fits) → Download → Start server. Backend can be forced to CUDA, Vulkan (Intel Arc / AMD) or CPU. The scripts below are what AIOS runs under the hood.

Step 2 — Build on Windows

# from C:\code\Work\llama, ordinary PowerShell
powershell -ExecutionPolicy Bypass -File .\build-llama.ps1

# options
.\build-llama.ps1 -Clean          # wipe build dir first
.\build-llama.ps1 -SkipInstall    # detect only, never winget-install
.\build-llama.ps1 -Branch b7400   # pin a tag/commit instead of master

What you will see, in order: a hardware summary (both GPUs with cc=12.0 and CUDA architectures: 120), toolchain checks, the clone or update, a CMake configure line, then a long compile — the CUDA kernels take 15–30 minutes on the 9800X3D the first time; later builds are incremental. It finishes with llama-cli --version and llama-server --list-devices, which must list CUDA0 and CUDA1.

Why Ninja, not the Visual Studio generatorThe Visual Studio generator needs CUDA's MSBuild integration, which is often missing on Build Tools-only installs and fails with "No CUDA toolset found". The script opens a VS developer shell and drives nvcc + cl through Ninja instead, which sidesteps that entirely.

Step 3 — Build on Ubuntu (walt-ai)

scp build-llama.sh run-qwen.sh walt-ai:~/llama/
ssh walt-ai
cd ~/llama && chmod +x *.sh
./build-llama.sh                  # --clean / --skip-install / --branch <ref>

On a fresh VM the script adds the NVIDIA apt repo matching the Ubuntu release and installs cuda-toolkit (toolkit only, so it never fights the driver the host passed through). If gcc --version is newer than that toolkit supports it installs g++-14 (or -15 for CUDA 13) and passes it as the CUDA host compiler. Ubuntu 22.04's CMake 3.22 is too old, so Kitware's repo is added there.

Static binaries on purposeThe build sets BUILD_SHARED_LIBS=OFF. With shared libs, a rebuilt llama-server can silently load a stale libggml-cuda.so from LD_LIBRARY_PATH and produce garbage output while everything looks healthy — the exact failure reported in llama.cpp discussion #27164 for this model.

Step 4 — Launch Qwen3.8-27B

.\run-qwen.ps1                              # default speed profile, http://0.0.0.0:8080
.\run-qwen.ps1 -BindHost 127.0.0.1          # local only
.\run-qwen.ps1 -Vision                      # + image input (downloads mmproj-F16.gguf)
.\run-qwen.ps1 -Ctx 262144 -KvType q4_0 -NoMtp   # full 256K context
.\run-qwen.ps1 -NoMtp -Parallel 4           # 4 concurrent slots (no MTP)
.\run-qwen.ps1 -Quant Q5_K_M                # trade speed for quality (any tag in the HF repo)
./run-qwen.sh                               # default speed profile, http://0.0.0.0:8080
./run-qwen.sh --host 127.0.0.1              # local only
./run-qwen.sh --vision                      # + image input (downloads mmproj-F16.gguf)
./run-qwen.sh --ctx 262144 --kv q4_0 --no-mtp    # full 256K context
./run-qwen.sh --no-mtp --parallel 4         # 4 concurrent slots (no MTP)
./run-qwen.sh --quant Q5_K_M                # trade speed for quality

The first run has llama.cpp itself download UD-Q4_K_XL (~17.5 GB) from unsloth/Qwen3.8-27B-GGUF into models/ (resumable; later runs reuse it), after printing the full command it is about to execute. The default command is:

llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL --jinja -ngl 999 -sm layer --no-mmproj \
  -c 65536 -fa on --cache-type-k q8_0 --cache-type-v q8_0 -b 2048 -ub 512 -t 8 \
  --parallel 1 --spec-type draft-mtp --spec-draft-n-max 2 \
  --host 0.0.0.0 --port 8080 --metrics

The OpenAI-compatible endpoint is http://<host>:8080/v1 — point OpenCode, Open WebUI or the latency monitor at it. The built-in chat UI is at /, Prometheus metrics at /metrics.

Step 5 — Benchmark and tune

Layer split is the safe default; whether row split wins depends on the PCIe lanes each card actually gets. Run both once and keep the faster:

.\run-qwen.ps1 -Bench                 # -sm layer
.\run-qwen.ps1 -Bench -Split row      # -sm row
# Ubuntu: ./run-qwen.sh --bench  /  ./run-qwen.sh --bench --split row

llama-bench reports pp512 (prompt processing) and tg128 (generation) in tokens/s. Row split can help tg by pulling bandwidth from both cards but often loses on consumer PCIe; the number decides. Note llama-bench does not exercise MTP — expect the live server to be 33–39 % faster at generation than tg128 shows.

Step 6 — Verify it works

  1. Both GPUs loaded

    While the server runs, nvidia-smi should show roughly 10–12 GB used on each card. If one card sits near zero, the split did not happen — check -sm and that --list-devices shows two CUDA devices.

  2. Coherent output

    curl http://localhost:8080/v1/chat/completions -H "Content-Type: application/json" -d '{"messages":[{"role":"user","content":"Explain the 9800X3D cache in two sentences."}]}'. Garbled or repeating text means a stale build, not a bad model — see Troubleshooting.

  3. MTP is active

    The server log prints draft acceptance statistics per request; acceptance around 0.75–0.82 is expected with n-max 2. If the log never mentions the draft, the GGUF lacks the blk.*.nextn.* tensors — use the unsloth repo.

  4. Stops cleanly

    Responses end at the model's turn without trailing chatter. If they ramble or get cut off, --jinja is missing or the template in the GGUF is old.

Why these settings

The build

Blackwell consumer cards are compute capability 12.0. That target is not in llama.cpp's default arch list and needs CUDA Toolkit 12.8 or newer, so the scripts read compute_cap from nvidia-smi, set CMAKE_CUDA_ARCHITECTURES=120, and upgrade the toolkit if the installed one is older. GGML_NATIVE=ON compiles for the 9800X3D's AVX-512 — it only touches the small CPU-side work, but it also means these binaries should not be copied to a different CPU. GGML_CUDA_FA_ALL_QUANTS=ON compiles the flash-attention kernels for quantized KV cache so q8_0/q4_0 caches run on the GPU rather than falling back.

HTTPS is compiled in — LLAMA_BUILD_BORINGSSL=ON on Windows, LLAMA_OPENSSL=ON with libssl-dev on Ubuntu — because llama.cpp no longer uses libcurl and -hf downloads fail with "HTTPS support disabled" otherwise.

The clone is always full-depth. A --depth 1 clone reports "Already up to date" while sitting hundreds of commits behind master, and the CUDA path for this model's DeltaNet layers was fixed on master recently — stale builds are the documented cause of corrupted Qwen3.8 output.

The model

Qwen3.8-27B is a hybrid: 48 linear-attention (DeltaNet) layers and 16 full-attention layers. Only the 16 full layers keep a KV cache, so context costs about 64 KB per token at f16 — a quarter of a conventional 64-layer model. 64K context in q8_0 is ~4 GB; even 256K fits in q4_0.

The weights do not fit one 16 GB card at any quant worth running, so the model is split. Layer split runs the cards in sequence, which means generation is bounded by one 5060 Ti's 448 GB/s — roughly 40 tok/s class for a 17 GB file — and the second card contributes capacity, not speed. MTP speculative decoding is where the speed comes from: the GGUF carries a multi-token-prediction head, and --spec-type draft-mtp --spec-draft-n-max 2 lets it propose two tokens per step at ~80 % acceptance for a 33–39 % gain. It currently requires --parallel 1, which matches the single-user priority; for concurrent slots drop MTP.

Flag reference

--jinja
Use the GGUF's Jinja chat template. Mandatory for Qwen3.8 — without it the turn boundaries and stop tokens are wrong.
-ngl 999
Offload every layer to GPU. 999 is "all" regardless of layer count.
-sm layer | row
How to divide tensors across the two cards. Layer = whole layers per card (default). Row = each matrix split across both; benchmark before adopting.
-c 65536
Context window in tokens. Model supports 262144.
-fa on
Flash attention. Required for quantized KV and the MTP path.
--cache-type-k/v q8_0
KV cache precision. q8_0 is visually lossless; q4_0 halves it again for very long context.
-b 2048 -ub 512
Logical / physical batch for prompt processing. Larger -ub costs VRAM for little gain on this class of card.
-t 8
CPU threads = physical cores. Nearly irrelevant once fully offloaded; keep it at 8 so SMT siblings don't fight the game/desktop.
--parallel 1
Request slots. MTP requires 1; each extra slot reserves its own share of the context.
--spec-type draft-mtp
Speculative decoding using the model's own MTP head instead of a separate draft model.
--spec-draft-n-max 2
Tokens drafted per step. 2 is the sweet spot measured for this model; 3 lowers acceptance.
--no-mmproj / -Vision
-hf downloads the 0.9 GB vision encoder by default; the scripts pass --no-mmproj unless you ask for -Vision.
--metrics
Prometheus endpoint at /metrics for the latency monitor.
CUDA_MODULE_LOADING=LAZY
Env var set by the launch scripts; faster startup and less VRAM for unused kernels.

Troubleshooting

nvcc fatal: Unsupported gpu architecture 'compute_120'
The CUDA toolkit is older than 12.8. Re-run the build script — it installs a newer one. On Windows, uninstall the old toolkit first if a cudart64_12.dll conflict appears after the upgrade.
#error -- unsupported GNU version (Ubuntu)
Host GCC is newer than the toolkit accepts. The script installs a supported g++-N automatically; with --skip-install, install it yourself and re-run.
No CUDA toolset found (Windows)
You ran CMake with the Visual Studio generator by hand. Use the script (Ninja) or copy CUDA's MSBuildExtensions into the Build Tools install.
Garbled, repeating, or empty responses
Almost always a stale build. Check git -C llama.cpp log -1 against GitHub master, re-run the build script, and confirm you launched bin/llama-server rather than another copy on PATH. It is not an MTP problem — the base model fails the same way without it.
Only one GPU is used
llama-server --list-devices must show two CUDA devices. On the Proxmox VM, both cards need to be passed through; on Windows, check CUDA_VISIBLE_DEVICES is unset.
Out of memory at load
Lower -Ctx, switch KV to q4_0, or pick a smaller quant. Close anything else holding VRAM (browsers with hardware acceleration count).
-hf fails with "HTTPS support disabled"
The binaries were built without an SSL library. Re-run the build script — it enables BoringSSL (Windows) or OpenSSL (Ubuntu).
-hf cannot find the quant
The tag after the colon must match a file in the repo (e.g. UD-Q4_K_XL, Q5_K_M). Pass it with -Quant.

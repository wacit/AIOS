Two Arc Pro B60s on the ProArt X670E

00 — What this box is, and the two numbers that shape it

Each Arc Pro B60 is a Battlemage (Xe2‑HPG) card with 20 Xe‑cores, 24 GB of GDDR6 on a 192‑bit bus (456 GB/s), a PCIe 5.0 x8 electrical link and a 120–200 W board power range. The Windows driver exposes about 20.8 GB per card, so plan on ≈41.6 GB of usable VRAM across the pair, and about 37 GB for weights once buffers and a 32K KV cache are paid for.

The second number is 64 GB of RAM, which is more than the VRAM. Every model that fits the cards also fits in RAM with margin, so AIOS reads the weights straight in (--load-mode none) instead of memory‑mapping them — the faster, quieter default on Arc. It also means the CPU side has room for a KV spill or a second small model without swapping.

Backend choice: SYCL (Intel's oneAPI backend) for dense models and anything split across both cards, Vulkan when you want MoE with several parallel slots and no toolkit. AIOS auto‑picks SYCL once oneAPI ≥ 2025.2 is installed. Everything below assumes SYCL; the Vulkan path is the same runbook minus phase 04 (AIOS adds VK_LOADER_DRIVERS_DISABLE=*radeon* on Vulkan so the Ryzen iGPU's driver stays out of the way).

01 — Hardware and power

The X670E‑Creator has two PCIe 5.0 x16 slots on CPU lanes that run x16/x0 with one card or x8/x8 with two. The B60 is only x8 electrical, so a card in each of the two CPU slots gets its full Gen5 x8 — nothing is lost to the split. The third slot is a chipset slot at x2 that is disabled by default; never put a GPU there.

M.2_1 and M.2_2 hang off the CPU separately and take nothing from the GPU slots, so NVMe for the models folder is free. Power: two cards at their 200 W ceiling plus a 9950X3D under load is about 650 W — an 850–1000 W PSU with a dedicated 8‑pin (or 12V‑2x6, depending on the partner card) lead to each card, no pigtails. Two open‑fan cards sit two slots apart on this board, which is enough airflow; a blower‑style B60 doesn't care. The B60 throttles quietly rather than crashing when hot, which shows up as decode speed that drifts down over a long run.

Gate 01: the board POSTs with both cards seated, the Q‑LED stays off, and the BIOS main page shows two PCIe devices on the CPU slots at x8.

02 — BIOS

This is the phase that bites — you have already seen it on the Z890 board: a BIOS update resets these to defaults, and the symptom is a card silently missing from Device Manager (or present with Code 12, "not enough free resources"). Two 24 GB BARs cannot be mapped below 4 GB, so the first setting is mandatory.

SettingValueWhy
Advanced → PCI Subsystem Settings → Above 4G DecodingEnabledLets the firmware place 24 GB BARs above the 4 GB line. Without it a card drops out or gets Code 12.
Advanced → PCI Subsystem Settings → Re‑Size BAR SupportEnabled / AutoFull‑VRAM BAR; Intel Graphics Software reports ReBAR off otherwise, and SYCL allocation is much slower.
Boot → CSM (Compatibility Support Module)DisabledReBAR needs a pure UEFI boot.
Advanced → Onboard Devices → PCIEX16_1 / PCIEX16_2 Link SpeedAuto (Gen5)Gen5 x8 per card. If a card trains unreliably (random drop‑outs, x4 or x1 after a warm boot), force Gen4 — the B60 loses nothing meaningful at Gen4 x8.
Advanced → Onboard Devices → PCIEX16_3 SlotDisabled (default)Enabling it halves M.2_3; it's x2 and useless for a GPU anyway.
Advanced → AMD CBS → NBIO → IOMMUEnabledHarmless on bare‑metal Windows; needed if this box ever runs WSL/Hyper‑V GPU passthrough.
Advanced → AMD CBS → Integrated GraphicsAutoLeave the Ryzen iGPU on for a display while the B60s compute; AIOS marks it integrated and never uses it.

Menu wording differs a little between ASUS BIOS revisions; the option names are stable even when their menu moves. Save with F10 and cold‑boot (full power‑off) after changing the 4G/ReBAR pair — a warm reboot sometimes keeps the old BAR map.

Gate 02: Windows Device Manager lists two Intel(R) Arc(TM) Pro B60 Graphics adapters (plus AMD Radeon(TM) Graphics, the iGPU) with no warning icons, and each B60's Properties → Resources shows a "Large Memory Range" spanning roughly 24 GB.

03 — Windows 11 and the Intel driver

  1. Edition. Windows 11 Pro. Apply all cumulative updates and the AMD chipset driver before the Arc driver.
  2. Driver. Install the current Intel Arc Pro WHQL graphics driver from intel.com (the Pro branch, not the consumer Arc package). Reboot. The build log in phase 05 needs driver ≥ 32.0.101.6xxx; the box you tested earlier had 32.0.101.8805, which is fine.
  3. ReBAR check. Open Intel Graphics Software → System → each GPU should show Resizable BAR: Enabled. If one card says Disabled, go back to phase 02 — it is never a driver problem.
  4. Power plan. Set the plan to High performance / Ultimate and disable sleep and disk idle; a sleeping host with 80 GB of weights mapped does not resume cleanly.
  5. Defender exclusion. Exclude C:\AIOS\models and C:\AIOS\bin; real‑time scanning of a 60 GB GGUF on every open is measurable.
  6. LAN access (optional). Start AIOS with --host 0.0.0.0 if other machines (OpenCode, Open WebUI, the latency monitor) should reach the GUI and llama-server.

04 — Toolchain (oneAPI ≥ 2025.2 is not optional)

llama.cpp's SYCL flash‑attention kernels reference the intel_gpu_bmg_g31 architecture enum, which only exists in the DPC++ compiler from oneAPI 2025.2 onward. The 2025.1 that winget ships fails at compile time with "no member named 'intel_gpu_bmg_g31'". build-llama.ps1 checks the installed version and, if it's missing or too old, downloads Intel's Deep Learning Essentials 2026.1 offline installer (~2 GB: DPC++, oneMKL, oneDNN, oneDPL) and runs it silently — expect a UAC prompt and 10–20 minutes. Everything else (Git, CMake, Ninja, VS Build Tools with the C++ workload) comes from winget with --source winget, which sidesteps the msstore certificate failure you hit on the Z890 box.

# Manual alternative, if you'd rather pre-install before the first build
winget install --id Git.Git -e --source winget
winget install --id Kitware.CMake -e --source winget
winget install --id Ninja-build.Ninja -e --source winget
winget install --id Microsoft.VisualStudio.2022.BuildTools -e --source winget --override "--quiet --wait --norestart --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"
# Intel Deep Learning Essentials (2026.1): download from intel.com/oneapi, then
.\intel-deep-learning-essentials-2026.1.3.20_offline.exe -a --silent --eula accept -p=NEED_VS2022_INTEGRATION=0

05 — AIOS and the build

  1. Run from C:\code\Work\AIOS (v0.3.6, scripts v6) or copy it to C:\AIOS. Only aios.py is strictly required — it rewrites the four scripts next to itself when they are missing or older than v6.
  2. Install Python 3.11+ (winget install --id Python.Python.3.12 -e --source winget). No pip packages are needed.
  3. Start it: python aios.py (opens http://localhost:7800).
  4. Section 1 should read: Ryzen 9 9950X3D · 64 GB · GPU0–GPU1 Intel Arc Pro B60 20.8 GB (intel/discrete), the Radeon iGPU tagged integrated · backend auto (sycl). If it says auto (vulkan), oneAPI isn't installed yet — that's fine, the build will install it.
  5. Section 2: backend auto, branch master (or the newest bNNNNN release for reproducibility), tick clean rebuild the first time, click Build.

06 — Serve

Which model fits

The AIOS recommender does this per quant, but the shape of the budget is worth seeing once. Per‑card overhead on SYCL is about 1.2 GB (compute buffers), and the KV cache scales with context.

Qwen3.8‑27B Q8_0
~29 + 8 + 2.5 GB
Qwen3.8‑27B UD‑Q4_K_M
~15 + 8 + 2.5 GB
Qwen3.6‑35B‑A3B Q4_K_M
~21 + 5 + 2.5 GB
Qwen3‑Coder‑30B‑A3B UD‑Q4_K_XL
~18 + 6 + 2.5 GB
Llama 3.3 70B IQ3_XXS
~28 + 10 + 2.5 GB — tight, low quality
weightsKV cache @ 32Kbuffersfree of 41.6 GB

Sizes are approximate. The 27B dense at Q8 and the two fast MoEs all fit comfortably at 32K context across the pair; a 70B only fits at 3‑bit with most of the context budget gone, which isn't worth it on this hardware. Start with Qwen3.8‑27B Q8_0 (dense, MTP draft head, the AIOS default) or Qwen3.6‑35B‑A3B (the fast MoE you already run).

Mode A — one model across both cards

In Section 3 leave both GPU boxes ticked, GPU layers 999, KV q4_0 (fastest on Battlemage; switch to f16 above ~16K context on SYCL), slots 1. Split: layer for MoE; for dense models try tensor — SYCL's tensor parallelism is tuned for exactly two cards and can beat layer split on decode. Benchmark both (phase 07). The command preview shows what AIOS will run:

ZES_ENABLE_SYSMAN=1 UR_L0_ENABLE_RELAXED_ALLOCATION_LIMITS=1 llama-server -m models\... --jinja -c 32768 -fa on
  --cache-type-k q4_0 --cache-type-v q4_0 -b 2048 -ub 2048 -t 16 --host 0.0.0.0 --port 8080 --metrics --load-mode none
  -ngl 999 -sm layer -mg 0 --parallel 1 [--spec-type draft-mtp --spec-draft-n-max 2]

For MoE models on SYCL, AIOS switches to -fa off (with the V cache back to f16, since a quantized V cache needs flash‑attention) and sets GGML_SYCL_DISABLE_OPT=1; both came out of your Arc benchmarks. --load-mode none appears because the weights fit in the 64 GB of RAM.

Mode B — one model per card

The natural two‑card layout for agent work: a general model on card 0 and the coding MoE on card 1, each on its own port. Untick one card, set the port, start; then start a second AIOS instance (or run by hand) for the other card. AIOS pins each process with ONEAPI_DEVICE_SELECTOR=level_zero:N so the servers never see each other's memory.

# By hand, after setvars.bat: card 1 only, on port 8081
set ONEAPI_DEVICE_SELECTOR=level_zero:1
set ZES_ENABLE_SYSMAN=1
set UR_L0_ENABLE_RELAXED_ALLOCATION_LIMITS=1
bin\llama-server.exe -m models\Qwen3-Coder-30B-A3B-UD-Q4_K_XL.gguf -c 32768 -fa off -ngl 999 -sm none -mg 0 --load-mode none --port 8081 --host 0.0.0.0 --metrics
Never start two SYCL servers on the same card; Level Zero doesn't arbitrate memory between processes and the second one fails late, after it has evicted part of the first.
Gate 06: the server pill turns ready, the log ends with srv update_slots: all slots are idle, and llama-server --list-devices in the log named the card(s) you expected.

Record pp512 (prefill) and tg128 (decode) for each model and split mode. A model that fits on one card is usually faster there than split across two (every split adds a PCIe hop); the split earns its keep on the models that don't fit, and on this board tensor is the one to watch for dense models. Your Coding Agent Latency Monitor (port 7900) can point at localhost:8080 for TTFT under load.

Gate 07: a chat completion returns coherent text (no repeated tokens — that means a stale binary), and llama-bench decode numbers are stable across the three runs (thermal throttling shows as a falling third run).

08 — Tuning knobs that matter on this box

KnobStartMove it when
Context -c32768KV cache is reserved up front on every card; go to 65K–128K only for long‑document work and drop KV to q4_0 or accept less weights headroom.
KV cache typeq4_0f16 above ~16K on SYCL (quality drift), q8_0 if a model shows odd punctuation at q4_0.
Micro‑batch -ub2048Already set by AIOS for Arc (≈+60% prefill). Lower to 512 if a long prompt OOMs on the first card.
Split -smlayer (MoE) / tensor (dense)Exactly two cards is what SYCL's tensor mode is tuned for; benchmark it per model. row is CUDA‑only.
Slots --parallel12–4 for several agents at once; the context window is divided between slots and MTP turns off.
--load-modenoneWith 64 GB of RAM every model that fits the cards also fits RAM, so AIOS reads the weights in instead of mmapping. (--no-mmap no longer exists on master.)
Threads -t16Only the un‑offloaded work uses them; on a fully offloaded model 8 is just as fast and leaves the host responsive for the desktop.
Power / clocksdriver defaultIntel Graphics Software exposes a power‑limit slider per card on Windows; 150 W each is the usual sweet spot — decode is bandwidth‑bound and barely notices, temps drop a lot.
